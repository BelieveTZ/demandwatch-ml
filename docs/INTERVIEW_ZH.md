# 项目定位、简历与面试路线

## 为什么选这个项目

已有 FinSight-RAG 体现检索增强生成、证据与 LLM 应用；地产交易游戏体现强化学习、
多智能体与决策。DemandWatch ML 补充监督学习、表格数据、时间序列、实验设计、
模型服务和 MLOps，形成第三条能力线。它适合补充机器学习工程师、应用算法、
AI 后端与初级 MLOps 岗位的作品证据；不代表已经覆盖视觉、语音或大模型训练岗位。

## 可用简历表述

**DemandWatch ML｜需求预测与模型监控平台**

Python / scikit-learn / FastAPI / SQLite / GitHub Actions

- 基于 UCI 共享单车 17,379 条小时记录构建可复现预测流水线，按时间划分训练、验证、
  校准和测试集，使用时间戳对齐的滞后特征与过去天气避免目标泄漏。

- 实现 FastAPI 预测服务、模型版本/校验、预测记录与延迟标签回传、PSI 漂移诊断，
  配套可交互回放仪表盘、自动测试与 GitHub Pages 展示。

## 十分钟演示顺序

1. 打开公开页面：说明真实历史测试集与离线回放的区别。
2. Overview：先解释两个朴素基线，再展示模型结果；切换到单周看曲线。
3. 找到早晚高峰切片：整体 94.98% 覆盖并不代表每个时段都达到 90%。
4. 本地运行训练和服务，Forecast Lab 选历史样例，运行真实推理；修改一个滞后输入，
   解释它是相关性驱动的假设场景，不是因果结论。
5. Monitoring：切换观测窗口与合成压力测试，解释日历/趋势告警可能是正常季节变化。
6. 用 OPERATIONS 中的脚本回传真实值，展示 MAE/覆盖率监控与模型版本隔离。
7. 展示测试：篡改未来目标/天气不会改变当前特征，缺失小时不会导致滞后错位。

## 必须能回答的问题

**为什么不用随机切分？** 相邻小时和季节结构有关联，随机划分会混入未来分布；
服务实际面对未来，所以选择、校准和最终评估必须按时间分开。

**为什么缺失小时不能直接 shift(24)？** 原始 CSV 缺少一些小时，24 行不一定是 24 小时。
先补齐时间索引但不填目标，再取小时滞后，排除所需历史不完整的预测点。

**测试集里的上一小时真实值算泄漏吗？** 对滚动一小时预测不算：假设上一小时已经结束并入库。
若要在今天一次预测未来 24 小时，则不能使用未来逐小时真实值，需要完全不同的回测。

**天气如何避免泄漏？** 不使用目标小时实测天气，仅使用前一小时观测。真实生产中如果
采用天气预报，还必须保存预报发布时刻并使用历史预报版本。

**为什么校准完不再训练？** 重新训练会改变预测器的残差分布，旧半径失去对应关系。
先固定预测器，再用专用校准区间计算有限样本修正分位数。

**94.98% 覆盖是否就很好？** 不一定。平均区间宽 147 次，夜间过宽，高峰欠覆盖。
时间相关性也破坏普通 conformal 的可交换性前提，不能宣称保证覆盖。

**PSI 报警能直接自动重训吗？** 不能。日历变化本就会漂移；应结合标签到达后的误差、
覆盖率、样本量与业务事件判断。本项目只有诊断，没有盲目自动重训/自动上线。

**下一步怎么做？** 预先留出新数据，增加多个滚动起点评估，比较异方差区间或分位数回归，
加入真实数据到达延迟和服务并发压测。不能不断用当前测试集挑最优版本。
